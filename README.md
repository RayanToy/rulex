## Задача

Тест на словарный запас — это набор заданий вида «выберите слово, которому
соответствует толкование». Чтобы собрать такой тест для 3–11 классов, нужны
тысячи заданий, и делать их вручную дорого.

Составить их по частотным спискам тоже не выходит: **списки зашумлены**.
Вот случайная выборка из `data/class_N_relative.csv`, на которой строится тест:

```
жоут        пажалст       иант        суэссоя      окситомипин
городнычий  почестьмить   немезид     пятисторонник
любовьювоспоминание       фельдшеров
```

Это OCR-ошибки, чатовые сокращения («пажалст» → «пожалуйста»), склейки двух
слов, искажения («городнычий» → «городничий»), словоформы вместо лемм. Рядом
с ними лежат совершенно нормальные редкие слова: *микробарограф, гипотензия,
инвар, пурин, кроманьонец*.

**Основная инженерная задача проекта — не генерация заданий, а отделение
реальных редких слов от мусора корпуса.** Отсюда и метрики ниже.

> [!NOTE]
> Проект создан при поддержке **Фонда содействия инновациям** в рамках программы
> «Студенческий стартап» федерального проекта «Платформа университетского
> технологического предпринимательства».

## Как это устроено

```
слово из частотного списка класса
        │
        ├─▶ 1. морфология (pymorphy3)          бесплатно
        │      часть речи, лемма, аббревиатуры
        │
        ├─▶ 2. сохранённый вердикт             бесплатно
        │      посчитан офлайн один раз для всего корпуса
        │
        ├─▶ 3. словари: OpenCorpora + Шаров    бесплатно
        │      слово есть в словаре ⇒ заведомо реальное,
        │      проверять моделью не нужно — это 61 % корпуса
        │
        ├─▶ 4. батч-проверка реальности        1 вызов на 30 слов
        │      только для того, что словари не знают
        │      при сбое батч ОТБРАСЫВАЕТСЯ, а не пропускается
        │
        ├─▶ 5. пригодность для теста           1 вызов
        │      не топоним, не этноним, не узкий термин
        │
        ├─▶ 6. дистракторы                     1 вызов
        │      гиперонимы/гипонимы, та же часть речи, не синонимы
        │
        └─▶ 7. толкование + коррекция          1–4 вызова
               без однокоренных с целевым словом
```

Пункт 3 — не оптимизация «на всякий случай», а результат проверки, нужен ли
платный шаг вообще. На наборе из 220 размеченных слов **каскад оказался лучше
любого из методов по отдельности**: F1 0.86 против 0.78 у словарей и 0.75 у
модели. Ошибки у них разные — словари уверенно подтверждают частотное, модель
разбирается с остатком. Плюс каскад покрывает 61 % корпуса бесплатно и
сокращает батч-вызовы с 3909 до 1521.

Разбор и данные: [eval/results/filter-cascade.md](eval/results/filter-cascade.md).

**Стек:** Python 3.11, FastAPI, SQLAlchemy (async), SQLite, pymorphy3,
Anthropic SDK, Docker.

## Что измерено

В проекте есть eval-харнесс: `eval/run_eval.py` прогоняет пайплайн по
фиксированному размеченному набору и считает метрики. Отчёты лежат в
`eval/results/` и версионируются вместе с кодом.

Наборы размечены вручную: **30 слов** для сквозных прогонов генерации
(`eval/words.tsv`) и **220 слов** для сравнения фильтров (`eval/words_220.tsv`,
149 реальных / 71 артефакт, стратификация 50/50 по словарной проверке).

### Отсев мусора корпуса

Положительный класс — `artifact`: recall показывает, какую долю мусора поймали.
Пропущенный артефакт попадает в тест как настоящее слово, поэтому из двух
ошибок эта дороже.

| Фильтр | precision | recall | F1 |
|---|---|---|---|
| Эвристики (гласные, буквосочетания) | 0.62 | **0.07** | 0.13 |
| Словари (pymorphy3 + Шаров) | 0.65 | 0.99 | 0.78 |
| LLM-фильтр (Sonnet 5) | 0.61 | 0.97 | 0.75 |
| **Каскад: словари → LLM** | **0.77** | **0.97** | **0.86** |

Эвристики на гласных и запрещённых буквосочетаниях ловят 5 артефактов из 71.
На меньшем наборе они не поймали вообще ни одного, а единственное их
срабатывание оказалось ложным: *всхрюкнуть* отбраковано по правилу «мало
гласных (20 %)», тогда как *пажалст* с 28 % прошло.

Разбор ошибок каскада: [eval/results/filter-cascade.md](eval/results/filter-cascade.md).

### Генерация заданий, до и после

| Метрика | До | После |
|---|---|---|
| **Доля успеха (yield)** | 0.105 (2/19) | **0.789 (15/19)** |
| Падений при разборе ответа | 14 | **0** |
| Латентность p50 | 12.4 с | **10.4 с** |
| Латентность p95 | 31.9 с | **22.4 с** |
| Утечка ответа в толкование | 0.00 | 0.00 |
| Совпадение части речи у дистракторов | 1.00 | 1.00 |

Главная причина роста в 7,5 раза — один дефект разбора ответа. Код брал
`response.content[0].text`, то есть **первый** блок ответа модели. У
современных моделей рассуждение включено по умолчанию, и первым приходит
`ThinkingBlock`, у которого поля `text` нет. Падало недетерминированно —
на 14 словах из 19.

Оставшиеся 4 отказа — редкие термины (*кроманьонец, микробарограф, пурин,
инвар*), к которым модель не подобрала дистракторов. Это ограничение, а не
сбой; см. [ниже](#ограничения-и-что-дальше).

### Выбор модели

Тем же харнессом сравнены шесть моделей — три облачные и три локальные
через Ollama: [eval/results/model-comparison.md](eval/results/model-comparison.md).

Коротко: **Sonnet 5 на генерацию, `ornith-1.5:9b` локально на фильтрацию.**
Фильтрация остаётся самым массовым шагом даже после каскада — около 46 тысяч
слов корпуса словари не подтверждают, — и там локальная модель даёт recall
0.91, столько же, сколько Haiku, но бесплатно. На генерации локальные
модели проигрывают качественно: `ornith` на слове «всхрюкнуть» придумала
значение и подобрала дистракторы к придуманному, так что верного варианта
в задании не оказалось вовсе. Ни одна облачная модель такого не сделала.

Обе версии qwen выбывают: у `qwen3:8b` recall 0.55 (половина мусора
проходит фильтр), у `qwen2.5:7b-instruct` — китайский текст в 16 %
русских толкований.

### Структурированные ответы

Три классифицирующих вызова — проверка реальности, пригодность для теста
и дистракторы — возвращают JSON по схеме через **строгий tool use**. Раньше
ответы разбирались строками (`"ПОДХОДИТ: да" in response.lower()` — причём
левая часть этого условия не срабатывала никогда).

Решения приняты по замерам, а не по документации:

| Вариант | Что показал замер |
|---|---|
| `output_config.format` | шлюз router.cheap **молча выбрасывает** параметр: ошибки нет, а модель отвечает markdown-списком с пояснениями |
| принудительный `tool_choice` | Sonnet 5 и Opus 5 отвечают **400**: принудительный выбор инструмента несовместим с рассуждением, включённым по умолчанию |
| `tool_choice: auto` + инструкция | Sonnet 5, Opus 5, Haiku 4.5 вызвали инструмент **3 из 3** раз |

На локальных моделях адаптер переводит инструмент в собственный параметр
Ollama `format`, так что код пайплайна для облака и Ollama одинаков. В живом
прогоне структурой пришло **20 ответов из 20 на обоих бэкендах**.

Разбор текста оставлен запаской, а харнесс считает долю структурных ответов:
совместимые шлюзы умеют выбрасывать параметры молча, и без счётчика этого
не видно.

Переход вскрыл три скрытых дефекта: markdown в ответе (`- **стол**`) не
снимался, и реальное слово считалось отвергнутым; проверка пригодности при
сбое API объявляла слово пригодным; а исчерпав попытки исправить толкование,
код сохранял **отказ модели** как толкование — «Я не могу создать толкование
для слова "микробарограф"…» попадало в банк вопросов с ответом прямо в тексте.

Последний дефект хорошо виден по трём прогонам Sonnet 5 на одном наборе:

| Прогон | Доля успеха | Утечка ответа |
|---|---|---|
| До перехода | 0.895 (17/19) | 6 % |
| Tool use без проверки толкования | 1.000 (19/19) | 16 % |
| **Tool use + проверка толкования** | **0.842** (16/19) | **0 %** |

Идеальная доля успеха в средней строке была **завышена**: отказы модели
засчитывались как готовые задания. Годных заданий в первой и последней
строке одинаково — 16, но битых теперь ноль.

### Офлайн-предфильтрация и Batches API

Вердикт «реальное слово или мусор» не меняется от запроса к запросу, а раньше
считался заново при каждой генерации. Теперь он считается один раз для всего
корпуса и хранится в `data/word_verdicts.tsv`:

```bash
python scripts/prefilter_corpus.py                  # весь корпус
python scripts/prefilter_corpus.py --classes 6 --limit 90
```

Задача возобновляемая: слова с готовым вердиктом пропускаются, а по
невыполненным запросам вердикт не пишется — они уйдут в следующий запуск.
Промпт и разбор ответа — те же методы генератора, что в живом пути, поэтому
предфильтрация **повторяет решения живого фильтра, а не вводит новые**:
качество фильтра она не меняет, меняется то, что оно считается один раз.

Модель вызывается через **Message Batches API**: он вдвое дешевле и не
упирается в лимиты на одновременность — а параллельные запросы через шлюз
работали впятеро медленнее последовательных. В обработчике запроса батчу
не место: он выполняется от минут до суток. Если эндпоинта нет, исполнитель
сам переходит на вызовы по одному. Так и вышло на практике: шлюз router.cheap
отвечает `404 Invalid URL (POST /v1/messages/batches)`, и живой прогон прошёл
через запасной путь.

> [!WARNING]
> Ветка Batches API покрыта тестами на фальшивом клиенте — порядок
> результатов, неудачные запросы, опрос, тайм-аут с отменой, 404 и клиент
> без батчей, — но **против настоящего эндпоинта не прогонялась**: доступный
> шлюз его не поддерживает, а у прямого ключа Anthropic нет средств.

### Слой данных

Схему ведёт **Alembic**, миграции применяются при старте приложения. Прежде
таблицы создавал `create_all`, который умеет только создать таблицу с нуля:
добавить в развёрнутую базу внешний ключ или новую таблицу им нельзя.

- **Сессии в базе**, а не в словаре внутри процесса. Раньше перезапуск
  разлогинивал всех, а при нескольких воркерах вход не работал вовсе.
  Хранится SHA-256 токена, а не сам токен.
- **Внешние ключи** вместо голых `Integer`, поведение при удалении выбрано
  для каждой связи. Удаление вопроса из банка обнуляет ссылку и **не
  стирает историю ученика**; удаление ученика каскадно удаляет его результаты
  и сессии.
- **Старая база обновляется без потери данных.** Ревизия 0001 повторяет
  схему прежнего `create_all` байт в байт, поэтому база без `alembic_version`
  распознаётся, помечается этой ревизией и доводится до актуальной.

Одна деталь SQLite, на которой легко ошибиться: внешние ключи применяются,
только если на **каждом** соединении выполнен `PRAGMA foreign_keys=ON`. Без
этого ограничения в схеме объявлены, но молча не работают. Есть тест, что
вставка ссылки на несуществующую запись действительно падает.

```bash
python eval/run_eval.py --dry-run     # только бесплатные эвристики, без API

```

Ответы кэшируются, повторный прогон на тех же промптах бесплатен.

## Запуск

```bash
git clone https://github.com/RayanToy/rulex.git
cd rulex
cp .env.example .env        # вписать ANTHROPIC_API_KEY
docker compose up --build
```

Приложение поднимется на `http://localhost:8000`.
**Первый зарегистрированный пользователь получает права преподавателя** —
без этого банк вопросов нечем наполнять. Дальнейшие назначения:

```bash
python scripts/make_admin.py --list
python scripts/make_admin.py ivanov
```

Без Docker:

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
pytest
uvicorn app.main:app --reload
```

## Структура

```
app/
  main.py             сборка приложения: lifespan, статика, роутеры
  api/                HTTP-слой: только разбор запроса и ответ
    auth.py           регистрация, вход, выход
    assessment.py     тест: выдача вопросов, проверка ответов, история
    questions.py      банк вопросов и генерация (только преподаватель)
    deps.py           зависимости FastAPI: текущий пользователь, права
    schemas.py        модели запросов Pydantic
  services/           предметная логика, ничего не знает про HTTP
    generator.py      пайплайн генерации: фильтры, дистракторы, толкования
    wordlists.py      частотные списки, словарь Шарова, сохранённые вердикты
    assessment.py     выбор вопросов, проверка ответов, адаптивная сложность
    llm.py            облако или Ollama за одним интерфейсом messages.create
    batches.py        Batches API с автоматическим переходом на вызовы по одному
  core/               инфраструктура
    database.py       движки, сессии, запуск миграций
    models.py         модели SQLAlchemy
    security.py       Argon2id, сессии в базе
migrations/           ревизии Alembic: схема, сессии, внешние ключи
eval/                 харнесс: words.tsv, metrics.py, run_eval.py, results/
tests/                pytest: целостность теста, доступ, чистые функции
scripts/              права администратора, офлайн-предфильтрация корпуса
data/                 частотные списки по классам + словарь Шарова
templates/index.html  разметка страницы
static/css, static/js стили и скрипт; ссылки на них версионируются хешем содержимого
```

Зависимости идут в одну сторону: `api → services → core`. Сервисы и ядро
не импортируют FastAPI, поэтому пайплайн вызывается из скриптов и
eval-харнесса без веб-сервера. Правило проверяет тест
`tests/test_architecture.py` — нарушение не сломало бы ни одного теста
поведения, поэтому оно проверяется по импортам в исходниках.

## Ограничения и что дальше

Честный список того, что в проекте пока не сделано или сделано не до конца.

**Измерения**
- Сравнение фильтров опирается на 220 размеченных слов — этого хватает.
  А вот метрики **генерации** считаются на 30 словах, и там разница в одно
  слово сдвигает долю на 0.05: повторные прогоны одной модели расходились
  по recall от 0.91 до 1.00. Различия меньше ~0.1 там от шума неотличимы.
- Разметка `eval/words.tsv` проставлена вручную и является суждением.
  Спорные случаи помечены в комментариях к строкам.
- **Стоимость вызовов не измерена.** Прогоны шли через совместимый шлюз,
  который возвращает `input_tokens = 0`. Харнесс это детектирует и помечает
  такие прогоны как недостоверные по стоимости — цифры в отчёте есть, но
  публиковать их как измеренные нельзя. Нужен прямой ключ Anthropic.

**Архитектура**
- `app/services/generator.py` — около 950 строк: весь пайплайн в одном
  классе. Следующий шаг — отдельные этапы (фильтр, дистракторы, толкование)
  с общим клиентом модели.
- SQLite: для одного сервера достаточно, но при нескольких экземплярах
  приложения нужна клиент-серверная БД. Миграции написаны без SQL, специфичного
  для SQLite, а batch-режим Alembic на других СУБД сводится к обычному
  `ALTER TABLE` — но на PostgreSQL они не прогонялись.
- Фронтенд — разметка и один скрипт на ~680 строк, без сборки и без
  браузерных тестов. Связь разметки со скриптом (обработчики `onclick`)
  проверяется только статически — тестом `tests/test_frontend.py`.

**Пайплайн**
- Толкование остаётся свободным текстом — остальные три вызова переведены
  на строгий tool use (см. [ниже](#структурированные-ответы)). Отказ модели
  на этом шаге теперь отбраковывает слово, но само толкование схемой не
  ограничено, и надёжность здесь держится на проверке после генерации.
- Генерация вынесена из event loop (`asyncio.to_thread`), но **параллелизм
  по умолчанию выключен — по результатам замера, а не из осторожности**.
  Пять параллельных задач на шести словах дали через совместимый шлюз
  251 секунду против 53 последовательных: запросы троттлятся и SDK уходит
  в ретраи. Локальная Ollama выигрыша тоже не даёт — она обслуживает один
  GPU и выполняет запросы по очереди. Повышать `RULEX_GEN_CONCURRENCY`
  имеет смысл только против прямого API и только с замером.
- Batches API подключён для офлайн-предфильтрации, но против настоящего
  эндпоинта не проверен: доступный шлюз отвечает на него 404.
- Проверка однокоренных слов сравнивает только леммы. Пары с чередованием
  (*книга / книжный*) так не ловятся. Пробовал заменить на стеммер Snowball —
  **стало хуже**: 4 правильных ответа из 12 против 6 у прежней эвристики,
  ложные срабатывания на *море/моряк*, *нос/носить*. Правильный путь —
  отдавать спорные случаи модели, а лемму использовать как быстрый фильтр.
